# Settlement (escrow, expiry, delivery, fees, caps)

Server side lifecycle of the player auction house. The client has no screen for it: results reach the player as system mail ("Ao concluir uma compra, o item será enviado via email do sistema", "Itens à venda ao expirarem, serão enviados via email do sistema"; `auction.view.AuctionHelp.helpContent` in `index/language.json`).

## 1. Overview

| Event | Effect |
|---|---|
| Listing created ([listing.md](listing.md)) | Item or Einherjar removed from the seller (escrow snapshot), custody fee `250 * hour` gold debited |
| Bid placed ([bidding.md](bidding.md)) | Bid amount debited from the bidder (escrow); previous highest bid refunded by mail |
| Buyout | Listing closed; buyer pays `fix_point`; highest bidder refunded; item mailed to the buyer; 80% of `fix_point` mailed to the seller |
| Expiry with a bid | Highest bidder wins at his bid; item mailed to him; 80% of the bid mailed to the seller |
| Expiry without a bid | Item mailed back to the seller; custody fee kept |
| Cancel (no bid) | Item mailed back to the seller; custody fee kept |

## 2. Screens

None in the auction module. Results are read in the mail screen ([../mail/README.md](../mail/README.md)). Mail type 5 `PET_MAIL` carries Einherjar (`decompiled/core_module/scripts/yishi/datas/consant/EmailType.as`); system mails are type 2.

## 3. Routes (client to server)

None specific. Claiming mail attachments is a mail route. The level gate and the daily cap are enforced inside the routes of [market-browse.md](market-browse.md), [listing.md](listing.md) and [bidding.md](bidding.md).

## 4. Server messages (server to client)

No auction opcode is pushed. Side pushes produced by settlement:

| Opcode | Name | When |
|---|---|---|
| mail module push | new mail notification | refund, delivery, income, return mails (see [../mail/README.md](../mail/README.md)) |
| 3 (0x0003) | `U_C_PLAYER_INFO` | diamonds or gold change of an online player (escrow and debits happen in the routes; settlement credits only through mail) |

## 5. Rules and formulas

- T1 Escrow: listing removes the item (or detaches the pet) in the same transaction that creates `auction.listing`; bids debit diamonds when placed.
- T2 Outbid refund: the full previous bid is returned by system mail with a diamond attachment (assumption: the player auction behaves like the system auction help "os diamantes que você usou para leiloar serão reembolsados para você via email").
- T3 Expiry: at `expires_at` the listing closes. With a highest bid: `status = 1`, item to the bidder by mail, seller income by mail. Without: `status = 3`, item back to the seller by mail.
- T4 Service fee: 20% of every completed transaction ("Para toda transação concluída, uma taxa de 20% do valor será descontado como taxa de serviço."). `seller_income = price - floor(price * 20 / 100)`. The fee is destroyed (diamond sink).
- T5 Daily purchase cap per buyer, by level (help lines 9 to 11): level 40 to 60: 2000 diamonds; 61 to 70: 3500; 71 to 80: 5000. Assumption: above 80 the cap stays 5000 (configurable). The counter adds every bid amount and buyout price debited today and subtracts refunds of bids placed today (assumption). Exceeding it returns -52 "Limite de compra diária através do leilão". Reset at 00:00 server time (assumption).
- T6 Level gate: every auction request below level 40 returns -51 "Leilão será liberado após atingir nv.40.".
- T7 Seller income mail: diamonds (non bound) `seller_income`; title and body generated by the server (no client template). Assumption: income is paid as normal diamonds.
- T8 Listing visibility delay ("Os itens leiloados apenas apareceram no leilão depois de algum tempo"): `visible_at = created_at + delay`. The original delay is unknown; assumption: 300 seconds, configurable. The seller sees his listing at once in "my listings".
- T9 Einherjar delivery: by mail type 5; the mail module must refuse the claim when the pet list is full ("Ao atingir número máximo de Einherjar, comprados no leilão não poderão ser retirados do email").
- T10 Expiry precision: a periodic job every 30 seconds (assumption) closes listings with `expires_at <= now()`; routes also treat an expired but still open listing as closed (-2) and trigger its settlement.

## 6. Templates

None. Constants to keep in configuration: custody fee per hour 250, service fee 20%, daily caps by level band, listing delay, expiry job period.

## 7. Persistent state

```sql
CREATE TABLE auction.settlement (
  settlement_id   BIGSERIAL    PRIMARY KEY,
  listing_id      BIGINT       NOT NULL UNIQUE REFERENCES auction.listing(listing_id),
  outcome         SMALLINT     NOT NULL CHECK (outcome IN (1, 2, 3, 4)),
  buyer_id        INTEGER      REFERENCES player.players(player_id),
  seller_id       INTEGER      NOT NULL REFERENCES player.players(player_id),
  price           INTEGER      NOT NULL DEFAULT 0,
  service_fee     INTEGER      NOT NULL DEFAULT 0,
  seller_income   INTEGER      NOT NULL DEFAULT 0,
  buyer_mail_id   BIGINT,
  seller_mail_id  BIGINT,
  settled_at      TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX settlement_buyer_idx ON auction.settlement (buyer_id, settled_at DESC);

CREATE TABLE auction.daily_spend (
  player_id   INTEGER  NOT NULL REFERENCES player.players(player_id),
  day         DATE     NOT NULL,
  spent       INTEGER  NOT NULL DEFAULT 0 CHECK (spent >= 0),
  PRIMARY KEY (player_id, day)
);

CREATE TABLE auction.refund (
  refund_id   BIGSERIAL    PRIMARY KEY,
  bid_id      BIGINT       NOT NULL UNIQUE REFERENCES auction.bid(bid_id),
  player_id   INTEGER      NOT NULL REFERENCES player.players(player_id),
  amount      INTEGER      NOT NULL CHECK (amount > 0),
  mail_id     BIGINT,
  created_at  TIMESTAMPTZ  NOT NULL DEFAULT now()
);
```

- `outcome`: 1 sold by bid, 2 bought out, 3 expired without bid, 4 cancelled (mirrors `auction.listing.status`).
- `*_mail_id` reference the mail module table (no FK across schemas until that schema exists).

## 8. Backend implementation notes

- `auction::settlement::run_expiry` (scheduler, every 30 s): `SELECT listing_id FROM auction.listing WHERE status = 0 AND expires_at <= now() ORDER BY expires_at LIMIT 200 FOR UPDATE SKIP LOCKED`; for each listing one transaction: close, insert `auction.settlement`, mark the winning bid status 2, create mails. Idempotent through the unique `listing_id` in `auction.settlement`.
- `auction::settlement::close_by_buyout(listing, buyer)`: called by `auction::bidding::handle_buyout` inside its transaction.
- `auction::settlement::refund_bid(bid)`: called by bid and buyout handlers; inserts `auction.refund` and a mail with a diamond attachment.
- `auction::settlement::check_and_add_daily_spend(player, amount)`: `INSERT ... ON CONFLICT DO UPDATE SET spent = spent + amount WHERE spent + amount <= cap RETURNING spent`; no row returned -> -52.
- Mail creation goes through the mail module API (`mail::system::send(player_id, title, body, attachments)`); attachments: item snapshot (recreated as a new item instance on claim), pet snapshot (mail type 5), diamonds.
- Server restart safety: the job also runs once at startup to settle listings that expired while the server was down.
