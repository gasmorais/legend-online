# Battle overview (Legend Online BR)

This is the entry point of `docs/battle/`. It summarizes how the Flash client runs a battle: the opcodes and their
routing, the battle model, the attack pipeline from packet to damage number, the battle scene, and the end of the
battle. Each topic is detailed, with `file:line` references, in the documents listed below.

**Conventions.** Source is the decompiled AS3 client. Path prefixes: **CM** = `decompiled/core_module/scripts`,
**M10** = `decompiled/m10/scripts`. Opcode names come from [`protocol/opcodes.csv`](../../protocol/opcodes.csv). Items
marked *(assumption)* are unconfirmed.

## 1. Opcodes and routing

`CM/yishi/service/managers/SocketManager.as:119-178` routes battle opcodes as follows:

| opcode | destination |
|---|---|
| **154** | `VictoryFailTransaction.handle` (direct, bypasses the queue) |
| **171** | `BattlePlotHandler` (plot dialogue) |
| **157** | `CoreTransactionManager` |
| **4102, 153, 156, 159, 72, 69, 77, 4149, 4361, 4600, 4752, 4793, 4795, 4849, 4589, 4311, 4591** | event `"GAME_CMD"` → `BattleTransactionManager.__gameCmdHandler` (`CM/battle/transaction/BattleTransactionManager.as:50,62`) |

### Entry

1. **157 U_B_PREPARE** (`BattlePrepareMsg`) → `CoreTransactionManager.handlerPackage`
   (`CM/yishi/manager/CoreTransactionManager.as:127-177`). With `total_page > 1`, pages are merged (heros, children,
   pets, soldiers, chessList). *Bug at line 148: `goddesses` is concatenated with `soldiers`.*
2. `CreateGameTransaction` (`CM/battle/transaction/CreateGameTransaction.as`):
   - `initBattleInfo` (99-188) builds `BattleModel`: battleId, mapTempId, battleType, side, countDown, coolDown. Units
     come from `createPawnRoleInfo` (`SoldierMsg`) and `createHeroAndPetRoleInfo` (`HeroMsg`:
     heros/pets/goddesses/children/monsters; 730-953).
   - `initBattleManager` (190-201) calls `BattleTransactionManager.setup`, `initSkillSystem`,
     `resourceModel.startLoad` and `EnterBattleController.handler`.
3. `CM/battle/control/EnterBattleController.as`:
   - shows `BattleLoadingView` and fires `"BATTLE_READ_GO"`, which triggers the preload (`BattleResPreloadManager`);
   - plays the transition `asset.core.EnterBattleSwitchMC` and calls `setScene("BATTLE_SCENE")`;
   - sends **10007 U_B_USER_LOADOVER** (`LoadOverMsg`: army_id, battle_id, server_name), or
     **10018 B_REINFORCE_LOADOVER** when `useWay ≠ 0`.
4. **156 U_B_START** (`BattleStartMsg`: frame, mainType, count_down) → `BattleStartTransaction`:
   `synchronization = frame`, `battleModel.started = true`, **`battleType = mainType`**, `hurtUpStart(countDown)`
   (`CM/battle/transaction/BattleStartTransaction.as:25-29`).
5. **153 U_B_ATTACKING** (`AttackOrderMsg`) → `BattleAttackTransaction` (pipeline in §3).

## 2. Model

`CM/yishi/datas/BattleModel.as`:

| aspect | fields |
|---|---|
| identity | battleId, battleType, mapId, mapResId, useWay, reinforceWave/currentReinforceWave, cooldownInfo |
| state | isOver, started, `_autoFightFlag`, `_hurtUpMode` |
| sides | `selfSide`; `armyInfoLeft` (always the own side) and `armyInfoRight` |
| units | `_roleList` (livingId → RoleInfo) and `_heroList` (key `"<row>_<side>"`, row = ⌊(pos−1)/3⌋: one hero per row) |

Time is **real time driven by frames**; there is no turn counter. Buffs (`cur_turn/max_turn`) and the fight mode
(`fmTurn`) carry turns, but they are **counted by the server**; the client only displays them and removes the buff at 0
([rules.md](rules.md) §13.2).

`CM/yishi/datas/objects/RoleInfo.as`:

| aspect | content |
|---|---|
| fields | livingId, side, pos (1-12), `face` (1 if own side, else 2), `bloodA/totalBloodA` (HP), `bloodB` (troop HP), sp |
| queues and actions | `BattleActionQueue`, `RoleSkillQueue`, concurrent actions, buffs |
| subclasses | Hero, Pawn, Monster, Pet and Goddess `RoleInfo`; each creates its view in `initView` |

**Clock:** `BattleManager._liftTime += _addFrame` per enterFrame, with `_standardFrame = 25`. `setBattleFrameRate` is
never called, so `_addFrame = 1`.

**Quicken:** `BattleQuickenControl` measures FPS and sets `speed = clamp(5 − ⌈fps/5⌉, 1, 5)`:

| FPS | ≥ 16 | 11-15 | 6-10 | 1-5 | 0 |
|---|---|---|---|---|---|
| speed | 1 | 2 | 3 | 4 | 5 |

Speed only increases the animation step (effects and hero body), not the clock. There is no speed button.

## 3. Attack pipeline

1. **Packet queue:** `BattleTransactionManager.enterFrame` (75-114) releases **at most one** packet per frame: the
   first, in arrival order, with `header.extend2 <= BattleFrameCount`. It is not strict FIFO: due packets overtake
   future ones.
2. **Read (153):** `BattleFunctionHelper.readSkill` (`CM/battle/utils/BattleFunctionHelper.as:151-249`) builds a
   `SkillData`:
   - fields: skillId, fId = attacker, liftTime = execution frame, sp, hitPoint;
   - `data[hit][target] = AttackData`, with `hits = damages.length / unique targets`;
   - `AttackData`: bloodType, damageValue, leftHp, extraData (bit 1 = critical), parry, resistances.
3. **Sync:** `SkillProcessStrategy.processSynchronization`, with `diff = server frame − local frame`
   (`SkillProcessStrategy.as:23-82`):

   | diff | effect |
   |---|---|
   | `< −20` | the local clock jumps to the server's |
   | `> 5` | the clock jumps, and pending skills of other roles with skillId ∉ 1..4, plus the own hero's default skills, are skipped; the new skill is never skipped |
   | `−20 ≤ diff ≤ 5` | the clock approaches by 20% per step, with integer truncation |

4. **SkillFactory:**

   | condition | skill class |
   |---|---|
   | −1 | `EmptyActionSkill` |
   | skill with TemplateId 105 (checked before ActionId 3/4 and `presentType`) | `SpecialActionSkill105` |
   | ActionId 3 | `SuccessSkill` ("Victory") |
   | ActionId 4 | `FailedSkill` ("Failed"). **No skill 4 or ActionId 4 exists in the local templates**, so defeat becomes an empty `BaseSkill` with no animation |
   | `presentType` 1 | `CommonActionSkill` |
   | `presentType` 2 | `ShootActionSkill` |

5. **Execution queues:** `SkillQueue` → `RoleSkillQueue`. A **single-target** skill whose target is running a
   `CommonActionSkill` has its liftTime pushed +1 per waiting frame. Then `BaseSkill.prepare` (skill name, `startRun`,
   buffs) and `CommonActionSkill.startRun`: passive effect `battle.resource.PassiveEffectAsset`, advance to the target,
   frame script, return.
6. **Skill frames:** XML template `ActionInfos` (ActionId, ActionType, Frame, Sex, Para as CSV). Frame types
   (`SkillFrameType`):

   | type | meaning |
   |---:|---|
   | 0 | advance |
   | 1 | attack animation (label = `Para[0]`) |
   | 2 / 5 | effect / "gas" |
   | 3 | DAMAGE |
   | 4 | zoom |
   | 6 | background color |
   | 7 | shake |
   | 11 / 12 | projectile |
   | 21 / 22 | jump |
   | 23 / 24 | displacement |
   | 25 | hide |
   | 99 | end |
   | 100 | return |

   Types 0 and 100 are read by the movement code, not by `SkillFrameExecuter`. `Para` CSV layout per type:
   [rules.md](rules.md) §5.2.

7. **Damage:** `BattleUtils.addSingleDanny` creates one `DannyAction` per target. `DannyAction.initHurt` flashes, plays
   "Danny" and calls `updateBlood(-dmg, crit, bloodType)`. Pending updates drain one per **3** `update()` calls
   (`CD = 2`). "Danny" plays only if the current label is `Stand` and damage > 0; buff damage neither flashes nor
   animates.
8. **Floating numbers:** `DamageNumView` at role point (0, −130); a critical rises 50 px more.
   - Animation: `asset.battle.BloodUpdateAsset` (normal) or `BloodUpdateRage` (critical).
   - Styles:

     | style | use |
     |---|---|
     | `battle.RedNumberAssetSp.text` | third-party damage (near white) |
     | `DamageNumberAssetSp.text` | damage dealt by the own hero (yellow) |
     | `SelfCauseNumberAssetSp.text` | parry (blue, scale 0.6) |
     | `GreenNumberAssetSp.text` | heal |
     | `CriticalDamageNumAssetSp` | critical |

   - `ParryAsset` and `CriticalDamageAsset` are created but **never shown**. Only bloodType 6 shows a value; 7 and 8
     show "0".
9. **bloodType** (`BloodType.as`): 6 HP, 7 troop, 8 third, 9 SP, 10 revive, 11 skill block, 21 max HP, 24 hitPoint,
   26 faith. 9, 24 and 26 only take effect when they arrive as buff damage.

## 4. Scene (M10)

- **Hierarchy:** `BattleSceneView` (`BATTLE_SCENE`) holds the background `battle.BattleBackGround` with `BattleView` on
  top. `BattleView` stacks: blurred background, `BattleMapView`, "profound" layer, `BattleUIView`, `RedScreenEffect`.
- **Visible area:** width 1000-1500 × height 600-900, clipped by `scrollRect`.
- **Camera:** `CAMERA_X = 650`, `CAMERA_Y = 900 − h/2`. Per-layer parallax:
  `x = −(cameraX − w/2) · moveCoefficient`, `y = −(cameraY · zoom − h/2)`.
- **Map:** `{RES}sceneIma/<BattleGround>/map<id>.swf`, class `ClassExport`.
  - Each MovieClip child is a layer with `moveCoefficient`, `repeat`, `moveSpeed`, `transparent`, `isFront`.
  - Layer order: backgrounds, roleBack, profound, roles (re-sorted by y every frame), effects, fronts, gas.
- **Actual maps:** all 17 `map<n>.swf` have a single layer, a 1500×900 bitmap at y −1. Since `RepeatBackGroundLayer.x`
  does not move the sprite, the image stays fixed at x 0-1500 (see [hud.md](hud.md) §13).
- **Position grid** (`BattleUtils.initRolePos` / `get9GridPos`; verified: `get9GridPos(295,570)` and `(905,570)`):
  - left: `(295 + 150·col − 40·row, 570 + 60·row)`;
  - right: `(905 + 150·col + 40·row, 570 + 60·row)`;
  - 3 columns × 4 rows: pos 1/4/7/10 = front column, 3/6/9/12 = back column, row = ⌈pos/3⌉ − 1. On the left side,
    `rolePointByPos` mirrors the column and `getPosition` does not. Full table in [formation.md](formation.md) §2.
- **Unit views** (`CM/battle/view/roles/`): Hero, Monster, Pawn, Pet, Goddess and SelfChess `RoleView`, over
  `RoleViewBase`.
  - Layers: shadow `asset.battle.RoleShadeMC`, back effects, body (`scaleX = −1` when face 2), effects, panel
    `asset.battle.PawnBottomAsset` with `battle.HeroNameTxt`.
  - HP bar: `asset.battle.BottomHpStripAsset`, or `BossBottomStrip` for the boss (`type 3`, face 2). The panel
    (name + bar) sits **at the unit's feet** (`PawnBottomAsset` at y = −20), not above the head.
- **UI** (`M10/battle/view/ui/BattleUIView.as`):
  - buttons `battle.AutoFightBtn2` (sends 10020), `battle.petChallenge.finishNowBtn` (sends 8727; only 35/307/16) and
    `battle.HideOthersBtn`;
  - bottom bar in **8 variants per battleType** (`BottomBar`, `PetBattleBar`, `PetSacristyBar`, `ChildpveBattleBar`,
    `ChildCommonBottomBar`, `MonsterCommonBottomBar`, `BattleSpaceTimeView` + `BottomBar`, or none), plus
    `SelfBloodView`, `SelfSpView` and `TeamStrip`. Full matrix in [hud.md](hud.md) §11.
- **QTE:**
  1. The client sends 10008.
  2. The server replies **75** (`HeroOrderMsg`), the generic reply to any skill request.
  3. The duration comes from `SkillTempInfo.QTETime` (template). With `QTETime > 0` and no auto-fight, `QteView`
     appears at `((w − qteW)/2, h − 280)` with `int(QTETime/1500)` keys (A/S/D/W or arrows); a miss restarts the
     sequence.
  4. On success the client sends 10015 after 400 ms; on failure it sends nothing.
  5. **All 22 716 local templates have `QTETime = 0`**, so the QTE never opens in BR.

## 5. End

1. **154 U_B_PREPARE_OVER** (`PrepareOverMsg`): `VictoryFailTransaction` creates one `SkillData` per unit
   (calcType 3 = "Victory", 4 = "Failed").
2. **4103 U_BATTLE_REPORT** (`BattleReportMsg`: battle_result 1 = win, 2 = loss, gp_bonus, baseItem[]...) →
   `BattleResultHandler`:
   - waits for all skills to finish (30 ms × up to 101 tries);
   - by default opens `VicotyBattleResultViewSimple` / `FailedBattleResultViewSimple` (`asset.battle.VictoryAssetII2` /
     `FailedAssetII2`). The detailed views (`VictoryAsset2/3`, `FailedAsset2/3`) are used only in battleTypes 16 and
     10; 3855 has its own Outyard views. There are no buttons: the screen closes on click or 1 s after the animation
     ends;
   - `exitBattle` picks the destination scene in a `switch(battleType)` (with `case` fall-through at 291 and 3911);
     `disposeBattle` comes from `BattleSceneView.leaving()`. Details in [hud.md](hud.md) §10 and [rules.md](rules.md)
     §7.
3. **4166 U_B_FIGHT_CANCELED** → `BattleManager.onFightCanceled`.

Replays: no code found. Only spectator mode exists (8985 C_BATTLE_VIEW and `battle_from == 1`).

## 6. Renderer preview

The viewer route `#battle:<preset>[@WxH][!map]` (for example `#battle:pve@1300x750!9`) renders the scene with the grid,
layers, the HUD with real assets, damage numbers, the 17 real maps, and soldiers, monsters and bosses from their real
SWF files. Heroes, children and pets use placeholders. Code lives in `web/src/battle/`; libraries in
`web/public/battle/` are generated by `python3 tools/battle_assets.py`. Details in [hud.md](hud.md) §13; the renderer
itself is described in [../client/renderer.md](../client/renderer.md).
