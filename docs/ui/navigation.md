# Navigation map

Every button of the castle HUD, what its click handler opens, and the socket traffic of each opened screen: the request opcodes it sends on open, the push opcodes it listens to and whether the local server answers them. Use it to follow a click from the HUD to a frame or scene and to find which flow rules are still missing.
Generated by `tools/navmap.py` from the decompiled AS3 in `decompiled/*/scripts`. Full data: `data/navigation.json`. Server rules for these screens: `server/flows/navigation.json`.

Related: [screen index](screens.md), [UI composition](README.md), [castle module m4](modules/m4.md), [socket protocol](../../protocol/socket.md), [protobuf messages](../../protocol/proto.md), [architecture overview](../overview/architecture.md).

## How to read this

Terms: a **request opcode** is a socket message the client sends (`send` in `protocol/opcodes.csv`); a **push opcode** is a message the server sends (`accept`). A **controller** is a class registered with `FrameControllerManager` that opens a frame; a **frame** is a PickGliss window; a **scene** is a full-stage state set by `SceneManager.setScene`.

| Column | Meaning |
|---|---|
| Button | Field of the view class. `.child` is the small second button of a `MainToolButton` |
| Style | PickGliss style name of the button |
| Label | Tooltip or text, resolved through `index/language.json` (pt-BR) |
| Opens | `key`(arg) > frame class: `FrameControllerManager.openControllerByInfo`. `getter.method`: a controller getter such as `armyController.startFrameByType`. `scene X`: `SceneManager.setScene`. `sends N, M`: request opcodes sent on click. `+N`: further targets not shown. `local only`: the handler neither opens a screen nor sends a request |
| Conditions | `enable`/`visible` assignments of the button and early `return` guards of the handler |
| Requests on open | Opcodes reached from the constructor, `start`, `show`, `init*`, `enter` of the controller, frame and its subviews. Static analysis: branches are not evaluated, so the list is an upper bound |
| Server | How many of those request opcodes have a rule in `server/flows.json` or `server/flows/*.json` |
| Listens | Number of push opcodes handled by the screen itself (manager listeners excluded) |

## Gaps

Known limits of the local server, followed by request opcodes of the main screens that have no rule yet.

| Area | Gap |
|---|---|
| mail | The mail list comes from the HTTP servlet `maillist` (zlib XML), not from the socket. `server/src/main.rs` answers it with `Result value=false`, so the Email frame opens empty |
| world map | Castle and wild land grids come from AMF (`/messagebroker/amf`) and opcode 5004 `sendCurrentScreen`; not answered |
| login data | `server/flows.json` consumes every `8224` login load, so bag, fashion, quests and friends are pushed on `8322 C_LEED_CLIENT` (templateId 1), which the client sends once right after the castle load |
| proto names | `protocol/proto.json` keeps one message per simple name. 25 names collide (ItemInfoMsg, PropertyMsg, PosMsg, ArmyMsg...). Rules use a donor with the same field numbers through `$type` (bag items use `SimpleItemInfoMsg`) or the field-1 alias (`PropertyMsg.temp_data` = `simple.PropertyMsg.param1`) |
| repeated scalars | The Rust encoder writes one tag per element of a repeated scalar. Fields that the AS3 reader decodes with `readPackedRepeated` need packed encoding, so rules leave those lists empty |
| Reino do Céu | No other players are injected (4597 player list) and node actions only work for nodes whose feature opens client side |
| space | No rule for 9676 C_EVIL_LAND_OP |
| campaign | No rule for 9006 C_DUNGEON_TURN_OP |
| castle | No rule for 9676 C_EVIL_LAND_OP |
| arena | No rule for 8265 C_QUICKCOOL_CHALLENGE_TIME |
| bag | No rule for 8346 C_BAG_REMOVE |
| hero | No rule for 8346 C_BAG_REMOVE |
| skills | No rule for 9724 C_LOTTERY_RUNE |
| guild | No rule for 8207 U_C_CONSORTIAUSER_LIST |

## Data file layout

Keys of `data/navigation.json`.

| Key | Content |
|---|---|
| `summary` | Counts and the list of view classes with mapped buttons |
| `buttons[]` | `group`, `view`, `field`, `style`, `style_class`, `tip_key`/`tip`, `label_key`/`label`, `handler`, `ref` (file:line), `conditions`, `guards`, `actions[]`. Dispatch entries (icons, buildings, queue items) also carry `dispatch` |
| `actions[]` | `type` controller/scene/frame/send. Controller: `key`, `arg`, `controller`, `frame`, `frame_class`, `screen`. Send: `code`, `name`, `msg`. `via` is the call chain |
| `screens{}` | Keyed `controller:<key>[#arg]`, `frame:<class>`, `scene:<class>`: `frame_class`, `title`, `subviews`, `sends_on_open[]` (with `answered_by`), `listens[]` (`code`, `msg`, `handler`, `class`, `scope` screen/manager), `global_managers`, `conditional_frames` |
| `roots[]` | Entry points per area (bag, hero, skills, shop, mail, friends, guild, tasks, arena, rooms, campaign, world map, space) |
| `scenes{}` | `SceneManager` key to class, from `yishi.scene.SceneCreate` |
| `opcodes` | Every request and push opcode seen, with message and `answered_by` |
